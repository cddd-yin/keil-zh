# 原理与兼容性

> 本项目的设计参照 GitHub 项目
> [`player4086/keil-uv5-zh-cn-patch`](https://github.com/player4086/keil-uv5-zh-cn-patch)
> 的“原文指纹”方案，并在此基础上增加了**对话框**覆盖与**原地汉化**模式。

## 1. µVision 的界面文字在哪里

µVision（`UV4.exe`）是原生的 Win32 / MFC 程序，界面文字都存在 PE 资源里：

| 资源类型 | 内容 | 例子 |
| --- | --- | --- |
| `RT_STRING`（6） | 字符串表 | 菜单项文字、状态栏提示、工具栏提示、快捷键 |
| `RT_MENU`（4） | 菜单模板 | 右键菜单、部分子菜单 |
| `RT_DIALOG`（5） | 对话框模板 | 对话框标题、按钮、静态文本、分组框 |

观察到的语言资源：

- `1033`（en-US）：主语言，字符串 955 条、菜单 39 组、对话框 216 个；
- `2057`（en-GB）：英文变体，少量；
- `1041`（ja-JP）：**仅字符串表** 534 条（没有菜单/对话框）——说明 µVision 的
  “本地化”只覆盖字符串表，这也解释了日文版为何没有日文对话框。

因此，**把 `1033` 资源替换为中文**即可让界面变中文，且与系统语言无关。

## 2. 词典与“原文指纹”

词典 `translations/zh_CN.json` 为 `format_version = 2`，结构要点：

```jsonc
{
  "target": { "version": "5.40.0.0", "sha256": "7063…" },   // 完整验证版本
  "translations": {
    "string_table": { "601": { "source_sha256": "…", "translation": "…" } },
    "menus":        { "22565": { "0/3/1": { "source_sha256": "…", "translation": "…" } } },
    "dialogs":      { "100":   { "title": { … }, "item:3": { … } } }
  }
}
```

- **键 = 资源身份**：字符串 ID / 菜单里的“索引路径”（如 `0/3/1`）/ 对话框里的
  `title` 或控件序号 `item:N`；
- **值 = 英文原文的 SHA-256 + 中文译文**。

生成器逐条比对本机 `UV4.exe`：

1. 用 Windows 官方 API（`LoadLibraryExW` + `EnumResource*` + `FindResourceExW`）读取资源，
   不执行目标程序；
2. 按资源身份取出英文原文，计算 `sha256(text.encode("utf-16le"))`；
3. 与词典中的 `source_sha256` 比对，**只有一致才写入译文**；
4. 写回时使用 `BeginUpdateResourceW` / `UpdateResourceW` / `EndUpdateResourceW`。

任何身份对不上、原文指纹对不上的条目，**一律保持英文**——这是“别错翻”的兜底。

## 3. 原地汉化的安全设计

为什么默认改写 `UV4.exe` 而不是生成副本？因为**桌面快捷方式、开始菜单、
文件关联、注册表**都指向 `UV4.exe`；只有就地改写，双击桌面图标才是中文。

安全措施（`build_patch.py`）：

1. **备份**：首次执行先把当前 `UV4.exe` 复制为 `UV4.exe.bak`；
   之后每次都**以这份备份为源**做指纹匹配，保证可重复、不会层层叠加；
2. **只写临时文件**：所有改动先落在 `UV4.exe.building`，写完做校验；
3. **写入前校验**（`compare_sections`）：逐段比较备份与待写入文件，
   `.text / .rdata / .data` 必须逐字节一致、只允许 `.rsrc` 变化；
   不满足则**放弃写入**，`UV4.exe` 保持原样；
4. **原子替换**：校验通过才 `os.replace`，避免半写状态；
5. **一键还原**：`tools/restore.py` 把 `UV4.exe.bak` 复制回 `UV4.exe` 并删除备份。

> 也可以 `--copy` 走非破坏式：只生成旁边的 `UV4_zh-CN.exe`，完全不动原版。

## 4. 版本识别与兼容模式

生成前先读取目标文件的 Windows 文件版本：

- 主版本号必须为 **5**，否则直接拒绝；
- 文件 SHA-256 等于词典 `target.sha256` → `exact-tested`，正常写入；
- 否则进入 `compatible-source-match`：仍按“身份 + 指纹”逐条匹配，
  但要求匹配率 `coverage.ratio ≥ --min-coverage`（默认 `0.70`）才允许写入，
  可用 `--exact-only` 强制只接受完整验证版本。不达标时脚本**不改动任何文件**，
  并以退出码 `2` 结束。

## 5. 只有资源段会变化

`tools/verify_pe_sections.py` 逐字节比较备份与汉化后的各 PE 段：

- `.text` / `.rdata` / `.data` / `.reloc` **完全相同**；
- 只有 `.rsrc`（资源段）发生变化。

因此本补丁不会修改程序逻辑、编译器驱动、调试器、Pack 或许可证相关代码。
唯一的副作用是**数字签名失效**（资源被改动，签名必然不匹配）——这是任何资源汉化
都无法避免的；如安全软件报警请自行评估或改用 `--copy` 模式。

`tools/validate_formats.py` 另外证明了菜单与对话框资源能被“解析 → 重新序列化”
**逐字节还原**（本机 40/40 菜单、246/246 对话框），说明改动没有破坏资源结构。

## 6. 为什么不做“二进制字符串”汉化

「关于 µVision」的许可正文、以及个别框架按钮（如属性表底部的 *Close / Help*）
是**以 ANSI C 字符串硬编码在 `.data` 中的**，不在资源里。要翻译它们必须改写
代码段/数据段字节，风险与收益不成比例（且对系统代码页有依赖）。本项目坚持
“只改资源”，把这些明确列为已知限制。
