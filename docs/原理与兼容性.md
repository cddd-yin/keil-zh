# 原理与兼容性

## 1. µVision 的界面文字在哪里

µVision（`UV4.exe`）是原生的 Win32 / MFC 程序，界面文字都存在 PE 资源里：

| 资源类型 | 内容 | 例子 |
| --- | --- | --- |
| `RT_STRING`（6） | 字符串表 | 菜单项文字、状态栏提示、工具栏提示、快捷键 |
| `RT_MENU`（4） | 菜单模板 | 右键菜单、部分子菜单 |
| `RT_DIALOG`（5） | 对话框模板 | 对话框标题、按钮、静态文本、分组框 |

观察到的语言资源：

- `1033`（en-US）：主语言，字符串 955 条、菜单 39 组、对话框 216 个；
- `2057`（en-GB）：英文变体，少量；
- `1041`（ja-JP）：**仅字符串表** 534 条（没有菜单/对话框）——说明 µVision 的
  “本地化”只覆盖字符串表，这也解释了日文版为何没有日文对话框。

因此，**把 `1033` 资源替换为中文**即可让界面变中文，且与系统语言无关。

> 为什么不是“新增 2052（中文）资源”？因为 Windows 资源加载会按线程语言回退，
> 行为不易预测；直接改写主语言 `1033` 更稳定、更可控。

## 2. 文本是怎么被“精确替换”的

1. 用 Windows 官方 API（`LoadLibraryExW` + `EnumResource*` + `FindResourceExW`）读取资源，
   不执行目标程序；
2. 解析出每个可翻译单元的**原文**（字符串表按 ID、菜单按路径、对话框按控件 ID）；
3. 在词典里查“**原文 → 中文**”的映射；
4. 写回时使用 `BeginUpdateResourceW` / `UpdateResourceW` / `EndUpdateResourceW`。

关键安全约束（`tools/build_patch.py: validate()`）：

- **格式符必须一致**：`%d %s %u %08X %1 %Ts %%` 等数量与内容完全保留；
- **快捷键后缀必须一致**：`新建(&N)\tCtrl+N` 的 `Ctrl+N` 原样保留；
- **助记符 `&` 数量一致**：`&File → 文件(&F)`，保证 Alt 键导航可用；
- 任一条不满足即**跳过该条**（保持英文）并在报告中列出，绝不强行写入。

词典里没有的原文、或原文与词典指纹不吻合的条目，**一律保持英文**——这是“别错翻”的兜底。

## 3. 只有资源段会变化

`tools/verify_sections.py` 逐字节比较原版与中文副本的各 PE 段：

- `.text` / `.rdata` / `.data` / `.reloc` **完全相同**；
- 只有 `.rsrc`（资源段）发生变化。

因此本补丁不会修改程序逻辑、编译器驱动、调试器、Pack 或许可证相关代码。
唯一的副作用是**数字签名失效**（资源被改动，签名必然不匹配）——这是任何资源汉化
都无法避免的；请只运行由本仓库源码在本机生成的副本。

## 4. 兼容性与版本匹配

- 词典按**原文指纹**匹配，而不是按版本号；
- 已验证版本：µVision **5.40.0.0**；
- 其它 5.x 版本：只要原文相同即可命中；新增/改动文案会保持英文，
  `--dry-run` 会给出匹配率与未命中项，便于评估。

> 这与“替换整个 `UV4.exe`”的老式汉化包有本质区别：**不会因为版本不符而
> 把不兼容的二进制塞进你的安装目录**。

## 5. 为什么不做“二进制字符串”汉化

「关于 µVision」的许可正文、以及个别框架按钮（如属性表底部的 *Close / Help*）
是**以 ANSI C 字符串硬编码在 `.data` 中的**，不在资源里。要翻译它们必须改写
代码段/数据段字节，风险与收益不成比例（且对系统代码页有依赖）。本项目坚持
“只改资源”，把这些明确列为已知限制。
